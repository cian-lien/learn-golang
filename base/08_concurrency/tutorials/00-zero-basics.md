# 从零开始：什么是并发，为什么 Go 适合做并发

这是整套教程的第 0 篇，写给完全没有并发经验的人。
你只需要会一点点 Go 语法（能看懂函数和 `for` 循环）就够，所有代码都可以直接跑。

读完这一篇你会明白三件事：并发到底在解决什么问题、`go` 这一个关键字做了什么、
以及为什么「等 goroutine 结束」是每个 Go 并发程序都要回答的问题。

**配套代码**：`examples/00_hello_concurrency/main.go`（全文不到 80 行）

```bash
cd go
go run ./base/08_concurrency/examples/00_hello_concurrency
```

## 一、先看一个「不并发」的程序

假设有三件事要做，每件要花 100 毫秒（比如三次网络请求）。最直白的写法是一件一件做：

```go
// taskDelay 表示每件事要花多久，100ms 是「能明显感觉到」的等待时间。
const taskDelay = 100 * time.Millisecond

// doWork 模拟一件需要等待的事：发一次网络请求、读一个文件、查一次数据库，
// 本质都是「发出请求，然后等结果」，代码里用 time.Sleep 来代表这段等待。
func doWork(name string) {
	time.Sleep(taskDelay)
	fmt.Println("    完成:", name)
}

func main() {
	start := time.Now()
	doWork("A")
	doWork("B")
	doWork("C")
	fmt.Printf("总耗时 %v\n", time.Since(start).Round(10*time.Millisecond))
}
```

运行结果：

```text
完成: A
完成: B
完成: C
总耗时 300ms
```

300 毫秒，因为三件事是**排队**做完的：第二件事要等第一件彻底结束才开始。

## 二、为什么并发能变快

把这 300ms 拆开看，其实 CPU 几乎没有干活：`time.Sleep` 期间，CPU 只是在**等**。
网络请求、数据库查询、读文件也都是这样——大部分时间在等，真正计算的时间很短。

打个比方：你去咖啡店买三杯咖啡。

- **串行**：点第一杯 → 站在柜台等它做好 → 拿走 → 再点第二杯 → 等 → …… 三杯花三倍时间。
- **并发**：一次性点三杯 → 咖啡师同时准备 → 你只需要等「最慢的那一杯」的时间。

你说的话（发请求）和咖啡师干活（对方服务器的活）是两件事，可以重叠。
**并发就是让「等待」和「别的活」重叠起来。**

当然它并不能让 CPU 变快：如果三件事都是纯计算（比如三次大数运算），
而机器只有一个核，并发不会让你少花时间。并发真正解决的是「等」。

## 三、进程、线程、goroutine

在 Go 里写并发，你只会接触一个词：**goroutine**。它和线程是什么关系？

| 名词 | 通俗理解 | 特点 |
|---|---|---|
| 进程 | 一个正在运行的程序 | 有独立内存，互相隔离 |
| 线程 | 操作系统调度的执行单位 | 创建成本高（MB 级栈），切换要陷入内核 |
| **goroutine** | Go 运行时调度的执行单位 | 初始栈只有 2KB，创建和切换都很便宜 |

可以把 goroutine 理解成「Go 帮你管理的轻量线程」。一个 Go 程序启动时只有一个 goroutine，
它就是执行 `main` 函数的那个，叫**主 goroutine**。你写的每一行代码，
默认都在某个 goroutine 里执行。

因为 goroutine 很便宜，Go 里「一个连接开一个 goroutine」「每个请求开几个 goroutine」
都是正常做法。几万个 goroutine 一起跑并不稀奇——它们大多在等 IO，不是真的都在用 CPU。

## 四、第一个 goroutine：`go` 关键字

让一件事在另一个 goroutine 里做，只需要在函数调用前面加一个 `go`：

```go
go doWork("A")
```

这一行的意思是：**把这次调用交给一个新的 goroutine 去执行，我不等它，继续往下走。**

于是并发版本长这样：

```go
func main() {
	start := time.Now()

	go doWork("A")
	go doWork("B")
	go doWork("C")

	time.Sleep(150 * time.Millisecond) // 先「猜」一个足够长的时间等它们做完
	fmt.Printf("总耗时 %v\n", time.Since(start).Round(10*time.Millisecond))
}
```

运行结果：

```text
完成: B
完成: C
完成: A
总耗时 150ms
```

两个现象值得注意：

1. **总耗时从 300ms 变成 150ms。** 因为三件事同时在等。
2. **完成顺序变成了 B、C、A。** 谁先做完是不确定的，所以并发程序里
   **不要依赖输出顺序**，这不是 bug，是正常现象。

至于为什么是 150ms 而不是 100ms：因为 `time.Sleep(150ms)` 是我们**猜**的，
猜多了 50ms。这正是下一个要解决的问题。

## 五、不能用「猜」来等人：WaitGroup 出场

如果加一件事，就得把 150ms 改成 200ms；如果某件事耗时变长，程序照样会出错——
它会提前打印结果，甚至直接退出，把还没做完的任务扔掉。

正确的做法是：**让每个 goroutine 做完后报个数，主 goroutine 等着数完。**
Go 标准库里的 `sync.WaitGroup` 就是干这个的：

```go
var wg sync.WaitGroup
for _, name := range []string{"A", "B", "C"} {
	wg.Add(1) // 还有一件事没做完
	go func(n string) {
		defer wg.Done() // 做完一件，报数
		doWork(n)
	}(name)
}
wg.Wait() // 阻塞在这里，直到一件都不剩
```

三个方法记住一句话就够：

| 方法 | 作用 | 类比 |
|---|---|---|
| `Add(1)` | 计数器 +1 | 「又派出去一件活」 |
| `Done()` | 计数器 -1 | 「我这件活干完了」 |
| `Wait()` | 阻塞到计数器归零 | 「等所有人都报数完毕」 |

运行结果变成了干净的 100ms，而且加多少任务都不用改等待逻辑：

```text
完成: C
完成: A
完成: B
总耗时 100ms
```

这里还藏了一个细节：`go func(n string)` 把 `name` 作为**参数**传进去。
在 Go 1.22 之前，如果直接在闭包里用循环变量，所有 goroutine 可能会拿到同一个值；
用参数传值是最稳、最容易看懂的写法（Go 1.22 起循环变量每轮独立，这是第 1 篇的内容）。

## 六、主 goroutine 退出，进程就结束了

程序最后还有一段：

```go
go doWork("没人等的任务") // 这个任务要 100ms 才完成
fmt.Println("main 执行到这里就返回了，上面那个 goroutine 等不到执行完")
```

运行后你会发现「完成: 没人等的任务」**从来没有被打印出来**。

原因很直接：**Go 程序不会等任何 goroutine，`main` 一返回，整个进程立刻结束。**
没有警告，没有「还有任务没做完」的提示，剩下的 goroutine 连同它们的栈一起消失。

这条规则解释了新手最常见的一类 bug：任务「偶尔」没执行、日志「偶尔」少打一行、
数据「偶尔」没写进去。遇到这种情况，第一反应就是问：

> **这个 goroutine 由谁负责等它结束？**

## 完整运行输出

```text
[1] 串行：三件事排队执行
    完成: A
    完成: B
    完成: C
    总耗时 300ms（每件 100ms，三件排队就是 300ms）

[2] 并发：用 go 让三件事同时进行
    完成: B
    完成: C
    完成: A
    总耗时 150ms（三件事同时等待，约等于一件的时间）

[3] 用 WaitGroup 正确地等待
    完成: C
    完成: A
    完成: B
    总耗时 100ms，而且不靠猜：有几个任务就等几个

[4] 主 goroutine 一退出，整个进程就结束了
    main 执行到这里就返回了，上面那个 goroutine 等不到执行完
```

第 2、3 部分的完成顺序每次运行都可能不同，这是正常的。

## 名词表

后面几篇会反复用到这些词，先混个眼熟：

| 名词 | 一句话解释 |
|---|---|
| goroutine | Go 里最轻的执行单位，用 `go` 启动 |
| 主 goroutine | 执行 `main` 的那个 goroutine，它一退出进程就结束 |
| 并发（concurrency） | 同时处理多件事的结构，让等待重叠 |
| 并行（parallelism） | 同一时刻真的在多个 CPU 核上执行 |
| 阻塞 | 代码停在那里等（等网络、等锁、等 channel），不占 CPU |
| 共享内存 | 多个 goroutine 都能读写的变量，容易出错 |
| 数据竞争 | 两个 goroutine 同时读写同一块内存，结果不确定 |
| 同步 | 协调多个 goroutine 的先后顺序或数据交换 |
| channel | Go 里用于在 goroutine 之间传递数据的管道（第 2 篇） |

## 常见疑问

**goroutine 会不会开太多？**
单个 goroutine 只占 2KB 左右的栈，开几万个没问题。真正要控制的是
「同时在途的请求数」，因为下游服务扛不住——这属于并发上限，第 5 篇讲。

**为什么加了 `go` 之后结果就不对了？**
最常见的原因是「没等它结束」（这一篇）或者「多个 goroutine 改了同一个变量」（第 4、7 篇）。

**并发和并行到底差在哪？**
并发是「同时处理」，并行是「同时执行」。单核也能并发（轮流跑），
多核才能并行。`GOMAXPROCS` 控制并行度，第 1 篇会细讲。

**怎么知道我的并发代码写对了？**
三个习惯：跑 `go run -race`、用测试覆盖并发路径、每个 `go` 都问一句「谁负责等它」。
